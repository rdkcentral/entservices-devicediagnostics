# DeviceDiagnostics Plugin Spec

## Overview

This specification covers all implemented capabilities of the `DeviceDiagnostics` Thunder plugin. The plugin exposes diagnostics and monitoring APIs for RDK-based devices, including device property retrieval, milestone logging, and AV decoder pipeline status reporting.

Scope: `GetConfiguration`, `GetMilestones`, `LogMilestone`, `GetAVDecoderStatus`, and the `onAVDecoderStatusChanged` event notification.


---

## Description

The `DeviceDiagnostics` plugin is a Thunder in-process plugin composed of two parts:

- **`DeviceDiagnostics`** — implements `PluginHost::IPlugin` and `PluginHost::JSONRPC`. Exposes JSON-RPC methods to external clients via autogenerated stubs (`Exchange::JDeviceDiagnostics`). Delegates calls to `DeviceDiagnosticsImplementation` running in the same process.
- **`DeviceDiagnosticsImplementation`** (in-process) — implements `Exchange::IDeviceDiagnostics`. Performs actual work: HTTP queries for device configuration, file I/O for milestones, and AV decoder state monitoring via the Essos Resource Manager (ERM) library.

The plugin runs in-process within the Thunder framework. `RPC::IRemoteConnection::INotification` is registered as standard Thunder plugin boilerplate; connection deactivation handling is present but the implementation runs in the same process as the plugin host.

### Capabilities

| Method | Description |
|---|---|
| `GetConfiguration` | Fetches device property values by name from a local configuration service |
| `GetMilestones` | Returns all lines from the RDK milestones log file |
| `LogMilestone` | Appends a marker string to the RDK milestones log |
| `GetAVDecoderStatus` | Returns the most active AV decoder/pipeline state at query time |
| `onAVDecoderStatusChanged` | Event fired when the most active AV decoder state changes |

## Requirements

### General
- The plugin MUST register using `SERVICE_REGISTRATION(DeviceDiagnostics, MAJOR, MINOR, PATCH)`.
- The plugin MUST implement `PluginHost::IPlugin` and `PluginHost::JSONRPC`.
- The plugin MUST expose JSON-RPC via the autogenerated `Exchange::JDeviceDiagnostics` stubs registered in `Initialize()` and unregistered in `Deinitialize()`.
- The plugin runs in-process. `DeviceDiagnosticsImplementation` is instantiated via `service->Root<>()` in the same process as the plugin host.

### GetConfiguration
- MUST accept a list of property names as input (`IStringIterator*`).
- MUST return a list of name-value pairs (`IDeviceDiagnosticsParamListIterator*`) and a `success` boolean.
- MUST return `success: true` when the backend service responds successfully (HTTP 0 or HTTP 200).
- MUST return `success: false` if the backend service is unreachable or returns an error.
- The backend service endpoint is an implementation detail (loopback HTTP service); the exact address is not part of the public API contract.

### GetMilestones
- MUST return the full contents of the milestones log file as a list of non-empty strings (`IStringIterator*`), one line per entry.
- MUST return `success: false` if the log file does not exist or cannot be read.
- Log file path: `/opt/logs/rdk_milestones.log`.

### LogMilestone
- MUST accept a non-empty `marker` string.
- MUST return `success: false` if `marker` is empty.
- MUST return `success: true` upon successfully writing the log entry.
- When `RDK_LOG_MILESTONE` is defined at compile time, the milestone is written via the `logMilestone()` system call.

### GetAVDecoderStatus
- MUST return the most active AV decoder/pipeline status as a string in `avDecoderStatus`.
- Valid status values: `"IDLE"`, `"PAUSED"`, `"ACTIVE"`.
- When compiled without `ENABLE_ERM`, the status MUST always be reported as `"IDLE"`.
- When `ENABLE_ERM` is defined, the status is read from the Essos Resource Manager (`EssRMgr`) without locking the polling thread's mutex.

### onAVDecoderStatusChanged Event
- MUST be fired when the most active AV decoder state changes from one polling cycle to the next.
- The event payload MUST include the field `avDecoderStatusChange` with one of: `"IDLE"`, `"PAUSED"`, `"ACTIVE"`.
- The event MUST NOT fire if the state has not changed since the last poll.
- This event is only active when compiled with `ENABLE_ERM`.

### AV Decoder State Machine

```
        ┌──────────┐
   ───▶ │   IDLE   │ ◀────────────────────────┐
        └────┬─────┘                           │
             │ any decoder becomes active       │
             ▼                                  │
        ┌──────────┐                            │
        │  PAUSED  │ ◀── active decoder paused ─┤
        └────┬─────┘                            │
             │ decoder plays                    │
             ▼                                  │
        ┌──────────┐                            │
        │  ACTIVE  │ ────────────────────────── ┘
        └──────────┘     all decoders stop/idle
```

State is determined by `EssRMgrGetAVState()` and polled every `AVDECODERSTATUS_RETRY_INTERVAL` (30 seconds).

### Notification Flow

```
AVPollThread                         DeviceDiagnostics (plugin host)
    │                                          │
    │── status changed ──▶ dispatchEvent() ──▶ Job::Dispatch()
                                               │
                                               ▼
                              INotification::OnAVDecoderStatusChanged()
                                               │
                                               ▼
                            JDeviceDiagnostics::Event::OnAVDecoderStatusChanged()
                                               │
                                               ▼
                                  JSON-RPC broadcast to all subscribers
```

## External Interfaces (if applicable)

### COM-RPC Interface

Defined in `IDeviceDiagnostics.h` (Exchange namespace):

```
IDeviceDiagnostics
  ├── Register(INotification*)
  ├── Unregister(INotification*)
  ├── GetConfiguration(names, paramList*, success)
  ├── GetMilestones(milestones*, success)
  ├── LogMilestone(marker, success)
  └── GetAVDecoderStatus(AvDecoderStatusResult*)

IDeviceDiagnostics::INotification
  └── OnAVDecoderStatusChanged(avDecoderStatusChange)
```

### JSON-RPC API

Callsign: `org.rdk.DeviceDiagnostics`

| Method | Parameters | Returns |
|---|---|---|
| `getConfiguration` | `names: string[]` | `{ paramList: [{name, value}], success: bool }` |
| `getMilestones` | none | `{ milestones: string[], success: bool }` |
| `logMilestone` | `{ marker: string }` | `{ success: bool }` |
| `getAVDecoderStatus` | none | `{ avDecoderStatus: string }` |

| Event | Payload |
|---|---|
| `onAVDecoderStatusChanged` | `{ avDecoderStatusChange: "IDLE" \| "PAUSED" \| "ACTIVE" }` |

### Configuration Service (GetConfiguration Backend)

- Protocol: HTTP POST to a loopback service
- Request body: JSON `{ "paramList": [{ "name": "<property>" }, ...] }`
- Response body: JSON with `"name"` and `"value"` fields per property
- Timeout: 30 seconds
- The service address is an internal implementation detail and is not part of the public API contract.

## Performance (if applicable)

- **AV decoder status polling interval**: 30 seconds (`AVDECODERSTATUS_RETRY_INTERVAL`). This means event delivery for state changes may lag by up to 30 seconds.
- **GetConfiguration timeout**: 30 seconds (`curlTimeoutInSeconds`). Callers of `getConfiguration` may block for up to 30 seconds if the backend is slow or unavailable.
- **GetMilestones**: Reads the full milestones log file synchronously. No size limit is enforced; large log files will increase response time.

---

## Security (if applicable)

- **`LogMilestone` marker validation**: The implementation rejects empty markers but applies no maximum length or character sanitization before passing the marker to the underlying log function. A maximum marker length SHOULD be defined and enforced.
- **`GetConfiguration` HTTP endpoint**: The backend is a loopback address (`127.0.0.1`), so external SSRF is not applicable. However, the endpoint is hardcoded; if the port is ever changed or the service is moved, this would require a code change.
- **Milestone log file**: Log file contents are returned as-is to the caller without sanitization. Consumers should treat milestone data as untrusted if it may be displayed in a UI.

## Versioning & Compatibility (if applicable)

- Current plugin version: `1.1.2` (Major=1, Minor=1, Patch=2).
- Interface version declared in `IDeviceDiagnostics.h`: `@json 1.0.0`.
- The JSON-RPC stubs are autogenerated from the interface header; any interface change requires regeneration of `JDeviceDiagnostics` and `JsonData_DeviceDiagnostics`.
- AV decoder status values (`IDLE`, `PAUSED`, `ACTIVE`) are derived from the ERM library constants. Additional states would require interface versioning.

## Open Queries

- **Configuration backend documentation**: The `GetConfiguration` implementation POSTs to `http://127.0.0.1:10999`. The identity of this service (TR181 agent, RFC, custom daemon?) is undocumented. A reference to that service's own spec or documentation would help.
- **`LogMilestone` marker length limit**: No maximum length is defined or enforced. Should there be a cap to prevent log bloat or buffer issues in the underlying `logMilestone()` function?
- **AV decoder polling latency**: 30-second polling means up to 30 seconds delay between a state change and the event being fired. Is this acceptable for all use cases? Is a configurable interval desirable?
- **`GetMilestones` file size**: The milestones log file is read entirely into memory with no size limit. Could this become a problem on long-running devices?
- **ERM status index bounds**: `decoderStatusStr[]` has indices 0 (`IDLE`), 1 (`PAUSED`), 2 (`ACTIVE`) followed by `NULL`. If `EssRMgrGetAVState()` ever returns a value outside this range, the plugin would read out of bounds. Should a bounds check be added?
