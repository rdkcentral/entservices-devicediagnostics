## Context

The DeviceDiagnostics plugin currently provides configuration retrieval, milestone logging, and AV decoder monitoring capabilities, but lacks an API to retrieve previous reboot information. Applications need this data to send diagnostic information to the SIFT monitoring endpoint for issue diagnosis and system health tracking.

The reboot information is persisted by the system during shutdown/reboot in two files:
- `/opt/secure/reboot/previousreboot.info` - Contains structured reboot metadata (timestamp, source, reason codes)
- `/opt/secure/reboot/hardpower.info` - Contains last hardware power reset timestamp

A similar implementation exists in the SystemServices plugin (`getPreviousRebootInfo2()`), which can serve as a reference for parsing logic and error handling patterns. However, DeviceDiagnostics has a different architecture (separate Implementation class, out-of-process support optional) requiring adapted implementation.

**Current State:**
- DeviceDiagnostics plugin uses autogenerated JSON-RPC stubs (Exchange::JDeviceDiagnostics)
- Implementation split between DeviceDiagnostics.cpp (plugin interface) and DeviceDiagnosticsImplementation.cpp (business logic)
- Plugin follows Thunder plugin guidelines for COM-RPC interface aggregation
- No existing reboot-related APIs in DeviceDiagnostics

**Constraints:**
- Interface definition (IDeviceDiagnostics.h) maintained in separate repository (ThunderInterfaces)
- Must follow existing plugin patterns (JSON-RPC stub registration, COM-RPC aggregation)
- File parsing logic must handle missing/malformed files gracefully
- Implementation must support both in-process and out-of-process execution modes

**Stakeholders:**
- Applications requiring diagnostic data for SIFT reporting
- DeviceDiagnostics plugin maintainers
- Thunder framework integration team

## Goals / Non-Goals

**Goals:**
- Add `getPreviousRebootInfo` JSON-RPC and COM-RPC API to DeviceDiagnostics plugin
- Parse reboot information from persistent storage files
- Return structured RebootInfo data with all six required fields
- Handle file read errors and malformed content gracefully
- Follow existing DeviceDiagnostics plugin architecture and coding patterns
- Ensure implementation works in both in-process and out-of-process modes

**Non-Goals:**
- Modify the reboot info file creation/writing logic (handled by system reboot scripts)
- Add file watching or automatic refresh of reboot data
- Implement caching of reboot information (read on-demand is sufficient)
- Change the format or location of reboot info files
- Add new event notifications (this is a query-only API)
- Port SystemServices.cpp implementation verbatim (adapt to DeviceDiagnostics patterns)

## Decisions

### Decision 1: Implementation Location

**Choice:** Implement in `DeviceDiagnosticsImplementation.cpp` (not in the main plugin class)

**Rationale:**
- Maintains separation of concerns: plugin interface vs. business logic
- Follows existing pattern used by GetConfiguration, GetMilestones, GetAVDecoderStatus
- Allows implementation to run out-of-process if configured
- Makes unit testing easier (mock file I/O in implementation class)

**Alternatives Considered:**
- Implement directly in DeviceDiagnostics.cpp: Would violate architecture pattern and complicate out-of-process support

### Decision 2: File Parsing Approach

**Choice:** Use line-by-line parsing with key=value format for previousreboot.info, single-line read for hardpower.info

**Rationale:**
- SystemServices.cpp uses this proven approach (leverage existing knowledge)
- Simple format doesn't require JSON or complex parsing libraries
- Handles partial/missing data gracefully
- Low memory overhead (no need to load entire file into memory structures)

**Implementation Details:**
```cpp
// Parse key-value format
string line;
while (getline(file, line)) {
    size_t pos = line.find('=');
    if (pos != string::npos) {
        string key = line.substr(0, pos);
        string value = line.substr(pos + 1);
        // Assign to appropriate RebootInfo field
    }
}
```

**Alternatives Considered:**
- JSON parsing: Overkill for simple key=value format, adds dependency
- Regex parsing: More complex, harder to debug, overkill for simple format

### Decision 3: Error Handling Strategy

**Choice:** Return `success: false` for file access errors, `success: true` with partial data if files readable but incomplete

**Rationale:**
- Consistent with other DeviceDiagnostics APIs (GetMilestones, GetConfiguration)
- Allows clients to distinguish between "no data available" vs. "partial data available"
- Matches SystemServices.cpp error handling patterns
- Provides maximum utility (partial data better than no data)

**Error Scenarios:**
| Condition | Behavior | success value |
|-----------|----------|---------------|
| Both files missing | Return empty RebootInfo | false |
| One file missing | Return data from available file | true |
| Parse error in file | Log error, return empty fields | false |
| Permission denied | Log error, return empty | false |
| Both files readable | Return all data | true |

**Alternatives Considered:**
- Always return `success: false` on any error: Too strict, loses partial data
- Throw exceptions: Not idiomatic in Thunder plugin context

### Decision 4: JSON-RPC Registration

**Choice:** Use autogenerated JSON-RPC stubs (Exchange::JDeviceDiagnostics::Register) after interface is updated

**Rationale:**
- Consistent with existing DeviceDiagnostics plugin pattern (GetConfiguration, GetAVDecoderStatus, etc.)
- Avoids manual JSON-RPC method registration and parameter marshalling
- Automatically handles JSON schema validation and error responses
- Reduces boilerplate code and maintenance burden

**Prerequisites:**
1. Add `GetPreviousRebootInfo()` to IDeviceDiagnostics.h in ThunderInterfaces repo
2. Rebuild Thunder code generator to produce JDeviceDiagnostics stubs
3. Registration happens in DeviceDiagnostics::Initialize()

**Alternatives Considered:**
- Manual JSON-RPC registration: Not recommended by Thunder guidelines, increases code complexity

### Decision 5: Thread Safety

**Choice:** No explicit locking required (files are read-only, no shared mutable state)

**Rationale:**
- Reboot info files are written once during boot, read multiple times
- No concurrent writes from within plugin
- Each API call creates local variables, no shared state mutation
- File I/O is inherently atomic at read level
- Follows same pattern as GetMilestones (also reads static files)

**Alternatives Considered:**
- Add mutex locking: Unnecessary overhead for read-only file access

### Decision 6: Logging Strategy

**Choice:** Log file access errors at ERROR level, successful reads at INFO level (if enabled)

**Rationale:**
- Consistent with existing DeviceDiagnostics logging patterns
- File access errors are rare and indicate system issues (warrant ERROR level)
- Successful API calls logged at INFO for audit trail (similar to GetConfiguration)
- Use LOGINFO/LOGERR macros from UtilsLogging.h

**Examples:**
```cpp
LOGERR("Failed to open previousreboot.info: %s", strerror(errno));
LOGINFO("Retrieved reboot info: timestamp=%s, reason=%s", timestamp.c_str(), reason.c_str());
```

### Decision 7: RebootInfo Structure Population

**Choice:** Initialize all fields to empty strings, populate from file data, return even if partial

**Rationale:**
- Guarantees structure always has valid (though possibly empty) strings
- Avoids undefined behavior from uninitialized members
- Clients can check for empty strings to detect missing data
- Matches SystemServices.cpp behavior

**Implementation Pattern:**
```cpp
RebootInfo rebootInfo;
rebootInfo.timestamp = "";
rebootInfo.source = "";
rebootInfo.reason = "";
rebootInfo.customReason = "";
rebootInfo.otherReason = "";
rebootInfo.lastHardPowerReset = "";

// Populate from files...
// Return even if some fields remain empty
```

## Risks / Trade-offs

### Risk: File Format Changes
**Description:** If system scripts change the reboot info file format, parsing will fail  
**Likelihood:** Low  
**Impact:** High (API returns incorrect data)  
**Mitigation:** 
- Use defensive parsing (check for '=' delimiter, handle missing keys)
- Log parsing errors to aid diagnosis
- Return `success: false` on format violations
- Document expected format in code comments

### Risk: File Location Changes
**Description:** Files might move to different paths in future platform versions  
**Likelihood:** Low  
**Impact:** High (API fails completely)  
**Mitigation:**
- Use #define for file paths to enable easy updates
- Consider reading path from configuration if flexibility needed
- Document file locations in header comments

### Risk: Permission Denied on File Read
**Description:** Process may not have read permissions on /opt/secure/reboot/  
**Likelihood:** Low (Thunder typically runs as root)  
**Impact:** Medium (API always returns failure)  
**Mitigation:**
- Check and log specific error codes (EACCES)
- Document required permissions in plugin README
- Platform integration team ensures correct permissions during deployment

### Risk: Missing Interface Definition
**Description:** This implementation requires corresponding changes to IDeviceDiagnostics.h in ThunderInterfaces repo  
**Likelihood:** N/A (coordination required)  
**Impact:** High (won't compile without interface)  
**Mitigation:**
- Coordinate with Thunder interfaces maintainers upfront
- Submit interface PR before or concurrent with implementation PR
- Add build-time check or comment referencing interface requirement

### Trade-off: No Caching
**Decision:** Read files on every API call instead of caching data  
**Rationale:** Reboot info is static per boot, caching adds complexity for minimal gain  
**Downside:** Slightly higher latency (file I/O on each call)  
**Upside:** Simpler code, no cache invalidation logic, always reflects current file content

### Trade-off: Partial Data Return
**Decision:** Return `success: true` with partial data if one file is readable  
**Rationale:** Partial diagnostic data is better than none  
**Downside:** Clients must check for empty fields  
**Upside:** More resilient to file system issues, maximizes data availability

### File Parsing Logic (Pseudocode)

```cpp
Core::hresult DeviceDiagnosticsImplementation::GetPreviousRebootInfo(
    RebootInfo& rebootInfo, bool& success) 
{
    // Initialize all fields
    rebootInfo = {}; // Empty initialization
    success = false;
    
    // Parse previousreboot.info
    ifstream file1("/opt/secure/reboot/previousreboot.info");
    if (file1.is_open()) {
        string line;
        while (getline(file1, line)) {
            size_t pos = line.find('=');
            if (pos != string::npos) {
                string key = line.substr(0, pos);
                string value = line.substr(pos + 1);
                
                if (key == "timestamp") rebootInfo.timestamp = value;
                else if (key == "source") rebootInfo.source = value;
                else if (key == "reason") rebootInfo.reason = value;
                else if (key == "customReason") rebootInfo.customReason = value;
                else if (key == "otherReason") rebootInfo.otherReason = value;
            }
        }
        file1.close();
    } else {
        LOGERR("Failed to open previousreboot.info");
    }
    
    // Read hardpower.info
    ifstream file2("/opt/secure/reboot/hardpower.info");
    if (file2.is_open()) {
        getline(file2, rebootInfo.lastHardPowerReset);
        file2.close();
    } else {
        LOGERR("Failed to open hardpower.info");
    }
    
    // Set success if at least one file was readable
    success = (!rebootInfo.timestamp.empty() || 
               !rebootInfo.lastHardPowerReset.empty());
    
    return Core::ERROR_NONE;
}
```

## Migration Plan

### Deployment Steps
1. **Pre-deployment:** Ensure ThunderInterfaces update is merged and available
2. **Build:** Compile plugin with new interface
3. **Deploy:** Standard Thunder plugin deployment (no migration needed)
4. **Verify:** Test API via JSON-RPC to confirm functionality

### Rollback Strategy
If issues arise post-deployment:
1. Revert to previous plugin version (API won't be available)
2. Or: Return `success: false` with empty data (safe degradation)
3. No data migration or cleanup required (query-only API)

### Compatibility
- **Backward Compatible:** Yes - adds new API, doesn't modify existing ones
- **Interface Versioning:** DeviceDiagnostics API version should be bumped (1.0.0 → 1.1.0)
- **Client Impact:** Opt-in feature - existing clients unaffected

## Open Questions

1. **Q:** Should we cache the reboot info after first read instead of reading files on every call?  
   **Status:** Design decision made - no caching (trade-off documented)
   
2. **Q:** Should the API support filtering/querying only specific fields (e.g., just timestamp)?  
   **Status:** Out of scope - return all fields always (matches spec requirement)
   
3. **Q:** What should happen if reboot info files are updated during plugin runtime?  
   **Status:** Not a realistic scenario (files written once at boot), ignore this edge case
   
4. **Q:** Should we add API versioning/capabilities to indicate this feature is available?  
   **Status:** Use standard Thunder plugin version bump (minor version increment)

5. **Q:** Do we need to support different file formats on different platforms?  
   **Status:** Assume single standard format - document expected format, platform team ensures compliance
