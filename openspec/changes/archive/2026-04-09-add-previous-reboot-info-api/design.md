## Context

The DeviceDiagnostics Thunder plugin currently provides various device diagnostic capabilities. The system persists reboot information in two locations:
- `/opt/secure/reboot/previousreboot.info` - JSON format with five fields: timestamp, source, reason, customReason, and otherReason
- `/opt/secure/reboot/hardpower.info` - JSON format containing lastHardPowerReset field

The plugin follows Thunder framework conventions:
- COM-RPC interfaces defined in `IDeviceDiagnostic.h` (ThunderInterfaces repository)
- Implementation in `DeviceDiagnosticsImplementation.cpp`
- JSON-RPC registration in `DeviceDiagnostics.cpp` using autogenerated stubs

Current constraint: The interface file `IDeviceDiagnostic.h` can be edited as part of this change.

## Goals / Non-Goals

**Goals:**
- Expose previous reboot information through Thunder COM-RPC interface
- Parse JSON from `/opt/secure/reboot/previousreboot.info` for five reboot fields
- Parse JSON from `/opt/secure/reboot/hardpower.info` for lastHardPowerReset field
- Return all six string fields in a RebootInfo structure
- Handle error cases with simplified error code (ERROR_GENERAL for all failures)
- Follow Thunder plugin lifecycle and coding conventions per project instructions

**Non-Goals:**
- Writing to or modifying the reboot info files (read-only access)
- Validating or enriching the reboot data (return as-is from files)
- Supporting other file locations or alternative data sources
- Providing historical reboot information (only most recent)
- Merging the two files into a single source
- JSON-RPC integration or registration (handled externally)

## Decisions

### Decision 1: Interface Method Signature and Data Structure
**Choice:** Define a `RebootInfo` structure in `IDeviceDiagnostic.h` containing six string fields, and add `virtual Core::hresult GetPreviousRebootInfo(RebootInfo& rebootInfo, bool& success) const = 0` to `IDeviceDiagnostic` interface.

**RebootInfo Structure:**
```cpp
struct RebootInfo {
    string timestamp;
    string source;
    string reason;
    string customReason;
    string otherReason;
    string lastHardPowerReset;
};
```

**Rationale:** 
- Uses Thunder's `Core::hresult` for error handling consistency
- Encapsulates all related fields in a single structure for cleaner API
- Boolean `success` parameter provides additional status indication beyond hresult
- Const method since it's read-only operation
- Better maintainability - adding fields in future only requires updating the struct
- Combines data from two separate files into a cohesive response
- **Alternative considered:** Five separate output parameters - rejected because structure provides better encapsulation and is easier to extend

### Decision 2: JSON Parsing Approach
**Choice:** Use Thunder's Core JSON utilities (`Core::JSON::IElement` or `JsonObject` from plugin context)

**Rationale:**
- Already available in Thunder framework (no new dependencies)
- Consistent with existing plugin patterns
- Tested and maintained by Thunder team
- **Alternative considered:** Third-party JSON library (jsoncpp, rapidjson) - rejected due to unnecessary external dependency

### Decision 3: Error Handling Strategy
**Choice:** Return `Core::ERROR_GENERAL` for all error scenarios with `success=false`.

**Error Scenarios (all return ERROR_GENERAL):**
- Either file doesn't exist or cannot be opened
- JSON parsing failure or malformed content in either file
- Any other I/O or processing error

**Partial Success Handling:**
- If previousreboot.info succeeds but hardpower.info fails: populate first 5 fields, set lastHardPowerReset to empty string, return ERROR_NONE with success=true
- If previousreboot.info fails: return ERROR_GENERAL with success=false (primary file required)

**Success Case:**
- `Core::ERROR_NONE` - success with all fields populated (empty strings if missing in JSON), success=true

**Rationale:**
- Simplified error handling reduces API complexity
- Single error code for all failures is sufficient for diagnostic/informational API
- Callers can check `success` boolean for simple pass/fail indication
- Empty strings for missing fields allow partial data exposure
- Follows Thunder error handling patterns
- **Alternative considered:** Multiple specific error codes (ERROR_OPENING_FAILED, ERROR_PARSE_FAILED, etc.) - rejected per user requirement for simplified error handling

### Decision 4: File Access Pattern
**Choice:** Open, read, parse, and close both files on each API call (no caching)

**Read Order:**
1. Read `/opt/secure/reboot/previousreboot.info` first (primary file - required)
2. Read `/opt/secure/reboot/hardpower.info` second (secondary file - optional)
3. Merge data into single RebootInfo structure

**Rationale:**
- Files update only on reboot (infrequent)
- Simple implementation with no state management
- No risk of stale cached data
- Minimal performance impact given infrequent access
- Reading on-demand ensures latest data if files are updated externally
- **Alternative considered:** Load once at plugin initialization - rejected because files may not exist yet at boot time
- **Alternative considered:** Cache with invalidation - rejected as unnecessary complexity for rare operations

## Risks / Trade-offs

**Risk:** File permissions may prevent reading `/opt/secure/reboot/previousreboot.info` or `/opt/secure/reboot/hardpower.info`  
→ **Mitigation:** Plugin likely runs with sufficient privileges; document required permissions; return ERROR_GENERAL with clear logging

**Risk:** JSON structure may evolve or vary across device types  
→ **Mitigation:** Parse only the documented fields; ignore unknown fields; return empty strings for missing expected fields rather than failing

**Risk:** Malformed JSON could crash parser in either file  
→ **Mitigation:** Wrap parsing in try-catch for both files; return ERROR_GENERAL on any parse exception; log detailed error for debugging

**Risk:** Inconsistent state if files updated independently between reads  
→ **Mitigation:** Files only written on reboot; minimal risk window; acceptable for diagnostic API

**Risk:** hardpower.info file may not exist on all device types  
→ **Mitigation:** Graceful degradation - return empty string for lastHardPowerReset if file missing; don't fail entire API call

**Risk:** File I/O on every call could impact performance if called frequently  
→ **Mitigation:** Document that this is diagnostic/infrequent API; consider adding rate limiting if abuse detected in practice

**Trade-off:** Using a structure vs. individual output parameters  
→ **Choice:** RebootInfo structure for better encapsulation and maintainability, with minimal overhead for COM-RPC serialization

**Trade-off:** Reading two files vs. requiring consolidated data  
→ **Choice:** Read from both sources to match existing system design; accept slight complexity for backwards compatibility with existing file structure

## Migration Plan

This is a new API addition with no migration requirements:

1. **Build Phase**: Interface changes require ThunderInterfaces rebuild and plugin recompilation
2. **Deployment**: No data migration needed (both files already exist on devices)
3. **Rollback**: Simply revert to previous plugin version; no persistent state affected
4. **Testing**: Verify on devices with and without existing reboot info files; test graceful handling when hardpower.info is missing

## Open Questions

None - design is straightforward with clear requirements and implementation path.
